Actores
Actores y Tokens en OIDC
Los componentes esenciales del protocolo
Roles (OAuth 2.0):
• Resource Owner — el usuario
• Client — la aplicación
• Authorization Server / OP — emite tokens
• Resource Server — API protegida
Los 4 tokens:
• Authorization Code (opaco, un uso)
• Access Token (JWT, para la API)
• ID Token (JWT, identidad al cliente)
• Refresh Token (opaco, larga vida)
Discovery
Discovery y JWKS
Cómo un cliente descubre al OP
Discovery Document:
GET /.well-known/openid-configuration
issuer, endpoints, capabilities, scopes_supported
JWKS:
JSON Web Key Set — claves públicas para validar firmas
kid identifica qué clave firmó el JWT
Flujo Principal
Authorization Code + PKCE
El flujo de login principal
1. Cliente solicita /authorize?code_challenge
2. OP muestra login + consentimiento
3. Usuario autoriza
4. OP redirige con ?code y state
5. Cliente canjea en /token con code_verifier
6. OP devuelve access_token + id_token (+refresh)
PKCE: proof key for code exchange — el code_verifier nunca viaja por el front-channel
state: anti-CSRF • nonce: anti-replay del id_token
Claims
ID Token y Claims
La tarjeta de identidad del usuario
Claims obligatorios: iss, sub, aud, exp, iat, nonce
Claims de binding: at_hash, c_hash, sid
Claims por scope:
• openid → sub
• profile → name, given_name, family_name, locale...
• email → email, email_verified
• address → address

Gestión
UserInfo, Introspection y Revocation
Consultas y corte de tokens
UserInfo: GET /connect/userinfo — devuelve claims del usuario con Bearer token
Introspection: POST /connect/introspect — verifica si token está activo. Responde active: true/false, nunca revela existencia de tokens ajenos.
Revocation: POST /connect/revocation — invalida tokens. Access token: registra jti como revocado. Refresh token: revoca familia completa.
Sesión
Gestión de Sesión y Logout
SSO, prompts y cierre de sesión
Tres tipos de sesión:
1. Sesión del OP (SSO — login silencioso)
2. Sesión del cliente (cookie propia)
3. sid (conecta id_token con la sesión del OP)
prompt: none (silencioso), login, consent, select_account
end_session: RP-Initiated Logout con id_token_hint
Avanzado
Flujos Avanzados
PAR, Device, CIBA e Híbrido
PAR (RFC 9126): ✅ Implementado — empuja parámetros por back-channel, recibe request_uri
Flujo Híbrido (code id_token): ✅ Para GAUDI — devuelve id_token en fragmento con c_hash
Device & CIBA: 🟡 Simulados — ciclo de sondeo sin pantalla real de autorización
Resumen
Matriz de Paridad
Teoría vs Real vs Mock
Tokens:
• authorization_code: 5 min (InMemoryCodeStore)
• access_token: 30 min (JWT RS256)
• id_token: 30 min (solo con scope openid)
• refresh_token: 8 h (rota, solo con offline_access)
Erros de protocolo (RFC 6749/7662/7009):
invalid_request, invalid_client, invalid_grant, unsupported_grant_type, invalid_scope
